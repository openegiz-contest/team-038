# Design decisions

Short record of choices made without a blocking question, newest last.

1. **Overlay, not core changes.** TwinVision joins the platform as `twinvision/compose.yml`, an overlay on `deploy/compose/docker-compose.yml`, with a marker file `deploy/compose/.twinvision`, exactly like the Example Mine. The only core edits are Makefile targets and one `.gitignore` line.
2. **One image for all Python services** (`twinvision/app:local`, `python:3.12-slim`, multi-arch), built by `twinvision-setup` only; other services use `pull_policy: never`, as the Example Mine explains.
3. **Grafana dashboards** are mounted over the platform's empty `/var/lib/grafana/dashboards` directory (Compose merges volumes by target), so they appear under the existing `openegiz` provider in a `TwinVision` folder without editing core provisioning files.
4. **Namespace** `org.twinvision.copper`; baseline twins use the suffix `-baseline` and their own root `mine-baseline`.
5. **Simulation clock**: fixed 1 s steps, 20x speed-up by default (`TWINVISION_SPEEDUP`), publish every 2 s real time. Roads, block clusters and the pit (slowly changing) are published every 5th tick. About 75 twins → roughly 20 Ditto updates per second for both copies.
6. **Common random numbers**: each entity (truck, excavator, block cluster) has its own seeded stream (`random.Random(f"{seed}:{kind}:{id}")`), so live and baseline only diverge through the consequences of a scenario.
7. **Fleet size 8 trucks** (Cat 793F class): with 9, all three shovels ran above their target rates and ore far exceeded plant demand. 8 gives a strip ratio of about 1.9 and a modest ore surplus to the ROM pad.
8. **Coarse ore stockpile live capacity 6,000 t (~3 h of plant feed)** is smaller than at real concentrators (often 12–24 h) so that a crusher failure visibly starves the plant within minutes of real time at 20x. Documented as a synthetic parameter.
9. **Scenario path through the platform**: the web API writes the `scenario-controller` thing in Ditto; Ditto republishes the change on MQTT `opentwins/twin/events/...`; the simulator subscribes to that topic and re-reads the thing over REST (plus a 30 s periodic re-sync and a read at start-up), so the scenario state survives a simulator restart.
10. **KPIs are 30-minute exponential averages** (simulated time), computed identically in both copies, so live-minus-baseline deltas are like-for-like.
11. **Block values from real data, spatial pattern synthetic.** Copper grades are drawn from the 2,000 drillhole assays and Bond work indices from the 60 grindability tests of the open GeoMet dataset (CC BY 4.0, see `DATA_LICENSES.md`) by quantile mapping of a seeded Gaussian-kernel field; each cluster uses a quantile range (north: high-grade hypogene, east: transitional, south: leached cap waste). An affine support correction (factor 0.7) shrinks 2 m assay variability to 10 × 10 × 15 m block scale.
12. **Energy from Bond's third law.** Crusher 0.0129 × BWi kWh/t (F80 ≈ 1 m to P80 ≈ 150 mm), concentrator (grinding plus ancillaries) 0.79 × BWi kWh/t plus 2.5 MW base load, which gives about 17 kWh/t, in the range reported for porphyry copper concentrators. Crusher capacity is limited by its 750 kW motor at the current feed hardness.
13. **Failures: wear-dependent hazard.** Hazard = λ0 · exp(k · (1 − health/100)); a failure occurs when the integrated hazard reaches an Exp(1) draw from the machine's own random stream. Initial health is spread from 45 to 95 % so that maintenance decisions appear within the first simulated hours. Parameters are synthetic, chosen to give mean times between failures of tens of operating hours for trucks and about 100 h for the crusher.
14. **Maintenance decision rule.** Every 15 simulated minutes, for each machine: plan maintenance if P(fail within 8 h) × MTTR × loss rate × 1.3 > PM duration × loss rate. Loss rate is in tonnes: a truck 900 t/h, an excavator its target rate (×1.5 for ore), the crusher plant demand minus what the coarse ore stockpile can cover plus a re-handling cost. If crusher maintenance only pays off with a full stockpile, the planner first raises the stockpile limit and the ROM loader builds stock, then releases the job.
15. **Fuel rationing rule.** Every 10 simulated minutes the dispatcher computes how many trucks must stop so that consumption ≤ resupply + bay stock / 12 h, keeps at least 3 trucks running and suspends the waste shovel first, so ore production is protected.
16. **Grid cap** limits only the concentrator (the crusher is small and feeds the buffer); plant throughput = (cap − crusher − base load) / specific energy. The 15-minute block demand is the usual billing interval for peak demand charges.
17. **Blending target** is the middle of the 0.55–0.85 % Cu band. The dispatcher adds a grade term to the excavator choice and diverts off-band ore to the ROM pad when it would push the coarse ore stockpile further from target; the ROM loader reclaims to correct the stockpile grade.
18. **Map UI without a frontend build chain**: plain HTML, CSS and SVG served by the FastAPI backend from the shared image. The backend discovers the twins with the Ditto search API, polls their features with one Ditto `GET /api/2/things?ids=...` per 40 twins every second and pushes snapshots to browsers with server-sent events; static geometry (benches, roads, blocks, facility positions) comes from the twins' attributes. Credentials never reach the browser. Trucks are animated along the road polylines between updates.
19. **Undo**: every action of the control API (one scenario on or off, reset all) is one entry on an in-memory undo stack that restores the previous properties of the affected scenario-controller features. The scenario state itself lives in Ditto, so it survives restarts of the web service; the undo history does not.
20. **Decision modules can be switched off, in the live copy only.** The switches are `*_module.enabled` features of the scenario-controller, so they go through Ditto like the scenarios and can be undone the same way. The baseline always runs with every module on, so live minus baseline is the value of the module. Fallbacks when a module is off: dispatcher → fixed truck-to-shovel allocation (2/2/4 trucks), ore always to the crusher unless it is down, no blending, no fuel rationing, no blend reclaim; maintenance → run to failure; energy → no throttling, and a 15-minute demand block above the grid cap trips the concentrator for 15 minutes (load shedding), which is what a protection relay or a utility interruptible-load contract would do.
21. **Energy manager.** Under a grid cap it limits the concentrator every step to (cap − crusher − base load) / specific energy, using the current feed hardness. It logs a decision when it starts or stops throttling or the limit moves by more than 5 %.
22. **Energy balance.** The grid meter integrates site power every step. The audit recomputes the same energy from its parts: fixed loads (crusher no-load, concentrator base) plus Bond specific energy × tonnes crushed and milled. Both are published, so a residual near zero means every kWh is attributed to a process.
23. **Decision logs** are bounded JSON strings (last 10 entries) in a single feature, so that InfluxDB keeps one string field per module and the UI needs no extra endpoint. The dispatcher logs only decisions that differ from the obvious choice (fastest shovel), with the reason, to keep the log readable.
24. **Commands without `make`.** `twinvision.sh` at the repository root runs the same steps as the make targets with only bash and Docker, for hosts where `make` is not installed.
25. **Twin inventory check.** `SCHEMA.md` holds a machine-readable inventory table; `check_twins.py` compares Ditto against it (types, counts per copy, parents, relation targets, truck relation features). The smoke test runs it.
